# Dify 知识库导入说明（chunks v2）

## 一、导入用文件

位置：`D:\WorkBuddy\项目\输出文档\chunks_v2\dify\`，共 5 个 `.md`，一本规范一个文件：

| 文件 | 规范 | 强制属性 |
|---|---|---|
| `GB 55031-2022 民用建筑通用规范.md` | 民用建筑通用规范 | 全文强制 |
| `GB 55037-2022 建筑防火通用规范.md` | 建筑防火通用规范 | 全文强制 |
| `GB 50352-2019 民用建筑设计统一标准.md` | 民用建筑设计统一标准 | 强条已废止（由 GB 55031 替代），技术参考 |
| `GB 55019-2021 建筑与市政工程无障碍通用规范.md` | 建筑与市政工程无障碍通用规范 | 全文强制 |
| `JGJ 38-2015 图书馆建筑设计规范.md` | 图书馆建筑设计规范 | 部分强条 |

每个分段的格式：

```
【GB 55037-2022】10.1.8（全文强制，P60）
除筒仓、散装粮食仓库和火灾发展缓慢的场所外，下列建筑应设置灯光疏散指示标志……
```

即首行是元数据（规范代号 + 条文号 + 强制状态 + 页码或页范围），第二行起是条文原文。
段与段之间用**单独一行的 `@@@`** 分隔。

## 二、Dify 端配置（三步，缺一不可）

### 1. 分段设置

上传时选择「**自定义**」分段，而不是「自动分段与清洗」：

| 项 | 必须填的值 | 原因 |
|---|---|---|
| 分段标识符 | `@@@` | 每个 `@@@` 恰好切出一条完整条文 |
| 最大分段长度 | **2000** | 默认值偏小会对长条文二次切分，破坏完整性；本批最长条文在 2000 字符以内 |

> ⚠️ 分隔符千万不要用 `====` 或 `---` —— Markdown 的 Setext 标题语法会把它们吃掉，产生空分段。
> 本批文件已用 `@@@`，且已强制 LF 换行（CRLF 会导致分隔符匹配不上）。

### 2. 索引方式

- 索引方式选「**高质量**」（需要 embedding 模型；向量检索比关键词检索更适合条文语义匹配）
- 若只能用「经济」，检索时以关键词为主，效果会下降但可用

### 3. 检索设置

- 检索方式：**混合检索**（向量 + 全文），二者权重可先各 0.5 再调
- 开启 **Rerank**（如已配置 rerank 模型）——规范条文数量不多，但「哪一条最相关」对 rerank 敏感
- Top K 建议 5～8；开启「Score 阈值」以过滤无关段落

## 三、跨规范冲突的处理（本项目的核心价值）

本项目涉及一个关键行业问题：**旧规范的强制性条文已被新规范废止**。

| 已废止的强条 | 现行替代 |
|---|---|
| GB 50016-2014《建筑设计防火规范》强条 | **GB 55037-2022**《建筑防火通用规范》 |
| GB 50352-2019 全部 4 条强条 | **GB 55031-2022**《民用建筑通用规范》 |

因此每条 chunk 都带了 `force_status` 元数据，检索命中后**必须连同规范名称与版本一起引用**，
不能只给条文号。建议在应用的提示词里写死这条规则，例如：

> 回答必须标注「规范名称 + 版本 + 条文号 + 强制属性」。
> 如引用 GB 50352-2019 的条文，须同时说明该标准强制性条文已由 GB 55031-2022 替代。
> 未在检索结果中找到依据时，明确回答「知识库中未找到对应条文」，不得推测。

## 四、导入前必看：待校对清单

`chunks_v2\校验报告.md` 与 `待校对优先清单.csv` 列出需人工核对的条目。重点看两类：

1. **疑漏号** —— OCR 漏读了某个条文号，该条正文被并进了前一条。
   报告里会给出去向（如「`2.9.4` 疑漏 `2.9.5`」）并展示本条末尾文字，
   对照原页在「。」处切开、补上条文号即可。**内容本身没丢**。
2. **表格 / 附录 chunk** —— 表格的 OCR 行列结构不可靠，数值务必对照原文核对后再用于设计。

## 五、不建议做的事

- **不要**把 `ocr_v2\` 里的原始 OCR markdown 直接导入 Dify —— 那是逐行 OCR 结果，
  既没有条文边界，也带着页眉页脚噪声。只导入 `chunks_v2\dify\` 里的文件。
- **不要**改动分隔符而不重新生成文件 —— 文件里的分隔符是 `@@@`，两边必须一致。
