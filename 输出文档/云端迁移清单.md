## 一、「改到云端」到底改什么

Dify Cloud 在公网，**够不到你本机的 `127.0.0.1`**。所以最省事、也是唯一不需要额外基建的迁移路径是：

> **放弃本机 Chroma 作为主链路，把 `chunks_v5` 灌进 Dify Cloud 的内置知识库，embedding 也换到云端。**

| 路线 | 卡点 | 判断 |
|---|---|---|
| **Dify Cloud 内置知识库** | 元数据只能挂文档级 | ✅ **采用** |
| 本机 Chroma + 内网穿透 + 外部知识库 API | 每次演示都依赖隧道存活；元数据过滤无 UI | 备选 |
| 自托管 Dify + 本机 Chroma | 要装 Docker（本机未装），起 16 个容器 | 暂缓 |

**走内置知识库的最大收益：不需要 Docker、不需要隧道、元数据过滤有 UI。**

## 二、🔴 动手前的 3 项前置检查（不通过就别建库）

### 1. Key 类型必须是「按量付费」

阿里云官方文档（Model Studio → Dify 接入页）原文：

> Dify 属于工作流/自动化平台，**不支持使用 Token Plan 个人版、Token Plan 团队版和 Coding Plan 接入**。这些套餐仅限在 AI 编程工具和 OpenClaw 类型 Agent 中使用。
> 在 Dify 中请使用**按量付费**的 API Key。将套餐 API Key 用于允许范围之外的调用将被视为违规或滥用，**可能会导致订阅被暂停或 API Key 被封禁**。

→ 去 [百炼控制台 API-KEY 页](https://bailian.console.aliyun.com/?apiKey=1#/api-key) 确认你用的是「按量付费」Key，不是包月套餐 Key。

### 2. 「使用国际端点」开关要和 Key 的地域一致

通义插件卡片的 API-KEY 设置界面有一个 **Use International Endpoint / 使用国际端点** 开关：

| 你的 Key 地域 | 开关 |
|---|---|
| 华北2（北京）· 中国大陆版 | **否** |
| 新加坡 · 国际版 | **是** |

设错 → 报 `Invalid API-key provided`。

### 3. 打开模型开关 + 用默认业务空间 Key

- 插件卡片里点 **「显示模型」**，把 **`text-embedding-v4`** 和 **`qwen3-rerank`**（或 `gte-rerank-v2`）的开关打开。
  **不开开关，建库时嵌入模型下拉框里根本找不到它，检索设置里也选不到 rerank。**
- 若报 `Invalid API-key provided` 且开关无误 → 大概率是**子业务空间 Key**（0.0.41 版插件会校验 `qwen-turbo` 调用权限）。改用**默认业务空间**的 Key。
- 千问插件由 **Dify 官方维护，非阿里云官方**，最新版偶有不稳；报错可按官方建议退回较早版本。

## 三、接下来怎么做：6 步

### Step 0 · 若 Dify 里已建过知识库
先确认它用的是哪个嵌入模型、哪种索引方式。**经济索引可升级为高质量，高质量不能降级为经济**；分段模式（通用/父子）建成后不可改。若已建成一个不合适的库，直接**新建一个**。

### Step 1 · 建知识库，只传 JGJ 38 一本
知识库 → 创建 → 上传 `chunks_v5\dify\JGJ 38-2015 图书馆建筑设计规范.md`

| 配置项 | 填什么 |
|---|---|
| 分段模式 | **通用**（父子模式本项目用不上，且不可改） |
| 索引方式 | **高质量** ⚠️ 硬约束 |
| 分段标识符 | `\n@@@\n` |
| 分段最大长度 | 拉到上限（4000） |
| 分段重叠长度 | `0` |
| 替换连续空格/换行符 | **关闭**（否则表格类 22 条被压成一行） |
| 删除 URL 和邮箱 | **关闭** |

### Step 2 · 点「预览块」核对
必须是 **222 段**。对不上就不要保存，回头查分隔符。

### Step 3 · 核对通过后传其余 4 本
同样配置。5 个 md 共 327,934 字节 / 0.33 MB，走 **网页 UI 批量上传**（API 有 10 次/分钟限制，留给定元数据用）。

### Step 4 · 建 5 个元数据字段并批量打值（API）
字段：`standard` / `standard_name` / `version` / `force_status` / `status`，类型全选 `string`。
代码见第六节。

### Step 5 · 检索设置（界面点选）

| 项 | 值 |
|---|---|
| 检索方式 | **混合检索** |
| Rerank 模型 | `qwen3-rerank`（或 `gte-rerank-v2`）⚠️ **必须启用**，否则 Score 阈值不生效 |
| TopK | 5 |
| Score 阈值 | 0.5 起调 |
| 元数据过滤 | 需要时加条件，如 `force_status = 全文强制` |

### Step 6 · 换 Chatflow 的知识库节点 + 验收
把原节点指向新库，**提示词 7 条铁律一个字不改**。
跑测试题，**D 组必须拒答**（9.9.9 不存在 / 智慧图书馆 0 命中）—— 这是唯一验收判据。

## 四、切分怎么保住

`chunks_v5\dify\` 5 个文件格式天生适配 Dify：

```
【JGJ 38-2015】1.0.1（部分强条，P10）
为保证图书馆建筑的设计质量，使其符合适用、安全、卫生、节能等基本要求，制定本规范。
@@@
【JGJ 38-2015】1.0.2（部分强条，P10）
本规范适用于新建、扩建和改建的图书馆建筑设计。
@@@
```

实测 JGJ 38 = **222 段**，与 `chunks.jsonl` 完全一致（无尾随分隔符）。

> ⚠️ 官方原文：**「分段模式（chunk mode）创建后不可更改；但分隔符、最大分段长度这类分段设置随时可调。」**
> 所以真正不可逆的只有「通用 / 父子」这个模式选择。即便如此，**先传一本核对 222 段**仍是最省事的做法。

## 五、元数据只能挂文档级 —— 但恰好够用

官方口径（Dify 官方 issue 答复原文）：**Metadata is only supported at the document level (not segment/chunk)**，且仅限内置知识库。

`chunks.jsonl` 实际跑一遍的结果：

| 字段 | 取值数 | 随条文变化？ | 结论 |
|---|---|---|---|
| `standard` | 5 | 否 | ✅ 可挂文档级 |
| `standard_name` | 5 | 否 | ✅ |
| `version` | 4 | 否 | ✅ |
| `force_status` | **3** | **否** —— 每本规范内只有 1 个值 | ✅ |
| `status` | 2 | 否 | ✅ |
| `chapter` | 13 | **是** | ❌ 丢 |
| `article_no` / `page_start` / `page_end` / `kind` | 逐条 | **是** | ❌ 丢 |

`force_status` 实测分布（「版本有效性」的落地）：

| 规范 | force_status | 条数 |
|---|---|---|
| GB 55019-2021 | 全文强制 | 119 |
| GB 55031-2022 | 全文强制 | 164 |
| GB 55037-2022 | 全文强制 | 275 |
| **GB 50352-2019** | **强条已废止(由GB55031替代)** | 303 |
| JGJ 38-2015 | 部分强条 | 222 |

**结论：你最看重的过滤维度（强制 / 参考 / 已废止 / 版本）全是文档级 —— 一分没丢。**
丢掉的是 `article_no` / `page` / `chapter` / `kind`，但它们**已经写在正文头部**（`【JGJ 38-2015】1.0.1（部分强条，P10）`），引用展示不受影响，只是不能拿它们做过滤。

> ❌ **绝不能按 chunk 拆成 1083 个文档**：免费版文档上限 **50**。

| Knowledge Documents | **50** | **5** | ✅ |

| Message credits | 200 条（一次性） | — | ✅ 已用自备 Key，不受限 |
| Apps | 5 | 1–2 | ✅ |
| API Rate Limit | 5,000/月 | — | ✅ |

**10 次/分钟是唯一真坑** → 5 个 md 在网页 UI 批量上传，API 只留给元数据（`documents/metadata` 是批量接口，5 个文档一次请求搞定）。

### 建元数据字段 + 批量打值

```python
import requests, time

BASE = "https://api.dify.ai/v1"
DS   = "<知识库ID>"              # 知识库页面 URL 里 /datasets/ 后面那段
H    = {"Authorization": "Bearer <知识库 API Key>"}   # 知识库 → 右上「服务 API」

# ① 建 5 个 string 字段
for name in ["standard", "standard_name", "version", "force_status", "status"]:
    r = requests.post(f"{BASE}/datasets/{DS}/metadata", headers=H,
                      json={"type": "string", "name": name})
    print(name, r.status_code)
    time.sleep(6)               # 避开 10 次/分钟

# ② 取字段 id
resp = requests.get(f"{BASE}/datasets/{DS}/metadata", headers=H).json()
fields = {f["name"]: f["id"] for f in (resp.get("doc_fields") or resp.get("data") or [])}
print(fields)

# ③ 一次请求给 5 个文档打值
META = {
    "GB 50352-2019 民用建筑设计统一标准":
        {"standard": "GB 50352-2019", "standard_name": "民用建筑设计统一标准",
         "version": "2019", "force_status": "强条已废止(由GB55031替代)", "status": "现行"},
    "GB 55019-2021 建筑与市政工程无障碍通用规范":
        {"standard": "GB 55019-2021", "standard_name": "建筑与市政工程无障碍通用规范",
         "version": "2021", "force_status": "全文强制", "status": "现行"},
    "GB 55031-2022 民用建筑通用规范":
        {"standard": "GB 55031-2022", "standard_name": "民用建筑通用规范",
         "version": "2022", "force_status": "全文强制", "status": "现行"},
    "GB 55037-2022 建筑防火通用规范":
        {"standard": "GB 55037-2022", "standard_name": "建筑防火通用规范",
         "version": "2022", "force_status": "全文强制", "status": "现行"},
    "JGJ 38-2015 图书馆建筑设计规范":
        {"standard": "JGJ 38-2015", "standard_name": "图书馆建筑设计规范",
         "version": "2015", "force_status": "部分强条", "status": "现行"},
}
docs = requests.get(f"{BASE}/datasets/{DS}/documents", headers=H,
                    params={"limit": 100}).json()["data"]
ops = [{"document_id": d["id"],
        "metadata_list": [{"id": fields[k], "name": k, "value": v}
                          for k, v in META[d["name"]].items()],
        "partial_update": False}
       for d in docs if d["name"] in META]
r = requests.post(f"{BASE}/datasets/{DS}/documents/metadata", headers=H,
                  json={"operation_data": ops})
print(r.status_code, r.text[:200])
```

> 文档名以上传到 Dify 后的**实际文件名**为准，先 `GET /documents` 看一眼再跑 ③。

## 七、模型与成本（已核）

| 项 | 值 |
|---|---|
| 嵌入模型 | **通义 `text-embedding-v4`**（Qwen3-Embedding 系列） |
| 维度 | 2048 / 1536 / **1024（默认）** / 768 / 512 / 256 / 128 / 64 |
| Dify 插件是否可调维度 | **否**（插件未暴露 `dimensions` 参数）→ 走默认 **1024 维** |
| 好处 | 与本地 Qwen3-Embedding-0.6B **同为 1024 维** → 可做 A/B 对照 |
| 单价 | 0.0005 元 / 千 token（Batch 接口 0.00025） |
| 免费额度 | 100 万 token（开通百炼后 90 天） |
| 单批上限 | 10 条文本，单条 8192 token |
| Rerank | `qwen3-rerank` / `gte-rerank-v2`（同一 Key） |

**总成本**：全库 1083 条 / 94,124 字 ≈ 14 万 token → **建一次库约 ¥0.07**，免费额度够重建七遍。

## 八、一句话总结

改动集中在一处：**把「本机 Chroma + 本地 0.6B 模型」换成 Dify Cloud 内置知识库 + 通义 `text-embedding-v4`。**
切分靠 `@@@` 分段标识符保住；元数据靠文档级字段保住核心过滤维度；拒答兜底靠**高质量索引 + 必须启用的 Rerank + Score 阈值**。
本机那套留着当离线备份与 A/B 对照，不删。
