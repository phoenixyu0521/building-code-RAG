```powershell

```

**这一步在干什么**：把「装了 chromadb 的那个 Python」存进一个变量 `$PY`。
你电脑里有**两个** Python —— 系统那个**没有** chromadb，用错了会报 `ModuleNotFoundError`。

**成功判据**：没有任何输出（PowerShell 里赋值成功就是静默的）。

**验证一下（推荐）**：

```powershell

```

- ✅ 成功：打印 `Python 3.13.14`
- ❌ 失败：`& : 无法将...识别为 cmdlet` → 说明你不在 PowerShell
- ❌ 失败：`系统找不到指定的路径` → 变量敲错了，重做 0.2

> **`&` 是什么**：PowerShell 的「调用运算符」。因为 `$PY` 是个字符串，得加 `&` 才能把它当命令执行。
> ⚠️ **`$PY` 只在当前这个窗口有效。** 关掉窗口 = 变量没了，下次要重设。

> 🔴 **最常见的一类报错（看到就知道是这个原因）**：
> ```
> 管道元素中的"&"后面的表达式生成无效的对象。该表达式必须生成命令名称、脚本块或 CommandInfo 对象。
> + CategoryInfo          : InvalidOperation: (:) []，RuntimeException
> + FullyQualifiedErrorId : BadExpression
> ```
> **原因**：这个窗口里 `$PY` 还没有值（新开的窗口 / 之前关过窗口）。**回到 0.2 重设一次就好**，不用怀疑脚本。
>
> **嫌变量麻烦的替代写法**：下面所有 `& $PY "xxx.py"` 都可以直接换成完整路径，一行搞定、不依赖变量：


**成功判据**：

1. 5 个批次**全部**打印出来，最后一行累计数是 **1083**
2. 出现 **`✅ 索引已落盘：4 个 .bin`** —— 这行才是真正的完成标志
3. 看到 `✅` 之后，**让程序自己结束**（回到 `PS` 提示符），**别按 Ctrl+C、别直接关窗口**

> ### ⚠️ 为什么这步最容易把库做坏
> **主因（已实测确认）：库目录含中文。** chromadb 1.5.9 的 HNSW 索引由 Rust 绑定落盘，
> 在中文路径下它**只写 `chroma.sqlite3`、不写那 4 个 `.bin`，并且不报错** ——
> 结果就是一个「sqlite 里 1083 条齐全、但一个 `.bin` 都没有」的半成品库，
> **连打开都会报 `Error loading hnsw index`**，只能删掉重来。**你之前那个坏库就是这么来的。**
> 库目录已改到 `D:\WorkBuddy\chroma_db`（纯 ASCII），脚本也会在启动时直接拒绝中文路径。
>
> **次因：落盘是异步的。** Chroma 把「压缩进 HNSW + 写 `.bin`」交给**后台线程**做，
> `add()` 返回**不代表**索引已写到磁盘。如果这时进程被杀（Ctrl+C / 关窗口），也会做坏库。
> 所有脚本已改成**主动等到 4 个 `.bin` 齐全才宣布成功**，所以只要看见「✅ 索引已落盘」就可以放心了。

> **两次运行的写法说明**：其实 `--stage all` 会把两段连着跑完。分开跑是为了让你**在慢的那段之后有个检查点** —— 出问题时你知道是哪一段的问题。

| 指标 | 意思 |

## 第 9 步 · 提交与上传（可选）

> **先分清两件事**（很多人在这里混淆）：
> - `git commit` = 把改动**存到本地仓库**。这一步做完，文件还在你自己电脑上，GitHub 上什么都没有。
> - `git push` = 把本地提交**上传到 GitHub**。这一步才是「传上云」。
>
> **所以第 9 步 ≠ 上传 GitHub**，它包含「本地存档 + 上传」两个动作，后者需要先配好远端仓库。

### 9.1 本地存档（commit）

```powershell

```

### 9.2 上传到 GitHub（push）—— **首次必须先建远端**

本项目**目前没有配置远端仓库**，直接跑 `git push` 会报
`fatal: No configured push destination`。首次上传要做这三件事：

**① 在 GitHub 网页上建一个空仓库**（不要勾 README / .gitignore / License，否则会和本地冲突）

**② 把远端地址告诉本地仓库**（只需做一次）：

```powershell
cd "D:\WorkBuddy\项目"

git remote -v                  # 能看到 origin 两行就算成功
```

**③ 首次推送要指定上游分支**（之后直接 `git push` 即可）：

```powershell

```

> 若提示账号密码：GitHub 已取消密码推送，**密码处要填 Personal Access Token**
> （GitHub → Settings → Developer settings → Personal access tokens，勾 `repo` 权限）。

### 9.4 仓库损坏修复（2026-09-13 实际踩过，已修好）

**症状**：`git commit` 报

```
error: invalid object 100644 <40位哈希> for '输出文档/scripts/xxx.py'
error: Error building trees
```

`git log` 依然只有老提交 —— **等于什么都没存进去**。

**根因**：3 天前一次 `git gc`（自动维护）**跑到一半被中断**。它的动作顺序是
「先把旧对象打包 → 打包成功后再删旧对象」，中断正好卡在中间 → **旧对象已删、新包没落地**，
`.git/objects/pack` 变成空目录，于是 5 个文件的内容永久丢失（索引还指着它们）。
同一次中断还留下 4 个 0 字节的陈旧锁：`index.lock` / `HEAD.lock` / `packed-refs.lock` /
`objects/maintenance.lock`，以及一个 0 字节残留临时文件。

**判据（两条命令）**：

```powershell
cd "D:\WorkBuddy\项目"
git fsck --connectivity-only          # 有 "missing blob ..." 就是它
dir .git\*.lock                       # 或看 .git 下有没有 0 字节的 .lock
```

**修复三步**：

```powershell
# ① 确认没有 git 进程在跑（任务管理器看有没有 git.exe），然后删陈旧锁
Remove-Item ".git\HEAD.lock",".git\packed-refs.lock" -Force -ErrorAction SilentlyContinue
Remove-Item ".git\objects\maintenance.lock" -Force -ErrorAction SilentlyContinue

# ② 让 git 从磁盘重新生成丢失的对象（哈希不变，因为文件内容没变）
git update-index --force-remove -- "输出文档/scripts/xxx.py"   # 对每个 missing 路径各做一次
git add -f -- "输出文档/scripts/xxx.py"
# 注意：--force-remove 后该文件变成被忽略状态，所以必须带 -f，否则加不回去

# ③ 复验再提交
git fsck --connectivity-only          # 应看到 "missing" 出现 0 次
git add -A
git commit -m "..."
```

**两条绝对不要做**：
1. **不要为了修复而跑 `git gc`** —— 打包过程本身就可能再次中断，风险比收益大。
   本仓库松散对象只有几十个，不打包完全没影响。
2. **不要 `git reset --hard` / `git checkout -- .`** —— 对象丢了不代表工作区丢了，
   文件都好好的在磁盘上，从磁盘重建即可，改了工作区反而真丢数据。

**下次预防**：`git log` 只见老提交、`git status` 却有一堆 `M`/`A`，就是「staged 但没能提交」，
先跑 `git fsck --connectivity-only` 而不是反复重试 `git commit`。
