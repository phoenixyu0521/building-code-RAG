## 一、目标与范围

### 1.1 终点是什么

一个**不依赖 Dify** 的命令行问答程序：输入问题 → 本地 Chroma 检索 → 拼提示词 → LLM 生成 → 输出带条文号的答案。

### 1.2 一个必须现在决定的架构问题：生成用谁

检索侧毫无疑问是本地（Chroma + Qwen3-Embedding-0.6B）。但**生成侧的大模型**有两个选择：

| 方案 | 生成模型 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）混合** | 通义千问 API（复用你 demo 那个 Key） | 质量好、零下载、当天可用 | 需要联网；检索命中的条文会发给阿里云 |
| **B 全离线** | Ollama 跑本地小模型（如 qwen2.5:7b） | **断网也能演示**、数据完全不出本机 | 多下 4～5 GB；CPU 推理慢（7B 约 3～8 token/s），回答要等十几秒 |
| C 双轨 | A 为默认，B 为「离线模式」开关 | 兼顾 | 工作量翻倍 |

**建议：先做 A，把 B 作为答辩前的加分项。** 理由：
- 你的 demo 已经在用千问 API，Key、提示词、参数都是现成的，A 可以直接复用；
- 合规上「上云不是红线」（规范是国家公开标准），已在 `README.md` 里改成了正确口径；
- 答辩现场通常有网；真要断网演示，B 随时能补。**别让"全离线"这个理想卡住主线进度。**

> 下面 §5 的步骤按方案 A 编排，B 在 §8 列为 P3 可选。

### 1.3 明确不做什么

- ❌ 不引入 LangChain / LlamaIndex（1083 条数据、单机自用，框架只增加抽象层和版本风险）
- ❌ 不启动 `chroma run`（那是服务端模式，我们用嵌入式 `PersistentClient`）
- ❌ 不改动 `chunks_v5` 的任何内容（它是已验收的基线）

### 4.1 P0：先修好库（§0 那个问题）

> ✅ **2026-09-13 21:5x 已完成。** 根因 = **库目录含中文**：chromadb 1.5.9 的 Rust HNSW 在非 ASCII 路径下**不写 4 个 `.bin` 且不报错**，必然做出打不开的库。

> **铁律：`CHROMA_DIR` 永远是纯 ASCII 路径，不要放回 `项目\` 或 `输出文档\` 下面。**

```powershell

# 1) 删掉坏库（整个目录）

& $PY "D:\WorkBuddy\项目\输出文档\scripts\build_index.py" --stage db
# 3) 验收
& $PY "D:\WorkBuddy\项目\输出文档\scripts\verify_index.py"
```

**验收判据（缺一不可）**：

1. 目录里出现 **4 个** `.bin` 索引文件（`header` / `data_level0` / `length` / `link_lists`）
2. `embeddings_queue` 归零
3. `col.count()` 返回 **1083**
4. 试检索能返回结果

### 4.2 关键改造：把「向量化」和「入库」拆开

上次中断的代价是**重跑 53 分钟**。改造成两段式后，这个代价会降到**几秒**：

```
[第 1 段] 读 chunks → 向量化 → 存 data\cache\embeddings_1083x1024.npy + ids.json
          ↑ 慢（53 分钟），但只做一次；文件在，重跑就跳过
[第 2 段] 读 .npy → add() 到 Chroma → 落盘
          ↑ 快（秒级），失败了多少次都能秒级重试
```

同时顺手加三条保护：

- **幂等**：开头先 `delete_collection`（或先 `get_or_create` 并检查 `count()`），避免重复累积
- **分批**：256 条一批，每批打印进度，让你知道卡在哪
- **优雅退出**：捕获 `KeyboardInterrupt`，提示「向量已缓存，重跑只需几秒」

> 这是本计划里**性价比最高的一项改造**：一次投入，以后每次重建库都省 53 分钟。

### 4.3 设计好检索接口

`app\retriever.py` 要封装的不是「一次 query」，而是这几个能力：

| 能力 | 为什么需要 |
|---|---|
| `search(query, top_k, where=None)` | 基础检索 |
| **元数据过滤** `where=` | 这是本项目的**核心行业价值**：可按 `standard` / `version` / `force_status`（强制/参考/已废止）筛。例如「只看现行强制条文」 |
| **`prompt_name="query"`** | ⚠️ **最容易漏的坑**：Qwen3-Embedding 内置一句英文检索指令，**查询侧必须带、文档侧不能带**。漏了检索质量明显下降 |
| 返回结构统一 | 每条含 `text` / `article_no` / `standard` / `force_status` / `score`，供拼提示词用 |

> 对照：Dify 内置库**锁死了切分与 embedding**，查询侧拿不到 `prompt_name` 指令 —— 这正是「本地版」在检索质量上能超过云端版的地方。

### 4.4 三个建库硬要点（沿用已验证的结论）

- `hnsw:space="cosine"`
- `normalize_embeddings=True`
- `documents` 存**原始正文**（不要只存向量，否则拿不回条文原文）

### 6.3 A/B 对照：本地 vs 云端（**这是能写进报告的核心实验**）

两边都用「纯向量 / 无 rerank / 无阈值 / TopK10」，唯一变量是 embedding 模型：

| 侧 | 命令 | 变量 |
|---|---|---|
| 云端 | `run_eval.py --backend dify --profile pure` | 通义 `text-embedding-v4`（1024 维） |
| 本地 | `run_eval.py --backend chroma --profile local` | `Qwen3-Embedding-0.6B`（1024 维） |

> 两边**同为 1024 维**，是刻意选的 —— 维度相同才便于对比；但**向量本身不可混用**（见 §7.1）。
> 注意：云端 hit-testing 有限流（Sandbox 10 次/分钟），86 条约 9 分钟；本地无限制。

### 6.4 调参顺序（别跳步）

```
① 固定 prompt + 固定 top_k=10 → 跑 baseline（云端 pure / 本地 local）
② 看「阈值窗口」报告：负例最高分 ↔ 正例金标 5% 分位
   ├─ 窗口存在 → 取中点设为阈值
   └─ 窗口不存在 → 说明「只调阈值」解决不了，要回到检索层
③ 扫 top_k / 是否加 rerank
④ 确定配置后，再跑一遍生成层 10 题做终验
```

## 七、从云端迁移到本地的注意事项

### 7.1 🔴 最重要的一条：**向量不能跨模型混用**

云端用通义 `text-embedding-v4`，本地用 `Qwen3-Embedding-0.6B` —— 即使**都是 1024 维**，两者是**不同的向量空间**，互相查询会得到垃圾结果。

推论：**本地库必须用本地模型从头建一次**，不能把云端的向量搬过来。这也意味着——

> 换 embedding 模型 = 1083 条全部重算 + 索引重建 + **Score 阈值重新标定** + 验收重跑。
> 这就是为什么「今天省 1 小时，以后赔一整天」，也是当初选本地模型的理由。**不要在这一步走回头路。**

### 7.2 ⚠️ 查询侧指令（本地独有的坑）

Dify 内置库帮你处理了这一步，本地得自己写：

```python
docs = model.encode(texts)                      # 文档侧：不加
q    = model.encode([question], prompt_name="query")   # 查询侧：必须加
```

漏掉 `prompt_name="query"` 不会报错，**只会让检索悄悄变差** —— 属于最难发现的那类 bug。写个单测锁住它。

### 7.3 阈值必须重新标定

云端配的 Score 阈值（0.5）**直接搬过来是错的** —— 不同模型的分数分布完全不同。
正确做法：跑 §6.1 的评测集，看它输出的**阈值窗口**，取中点。

> 🔴 **2026-09-13 实测更新：本地根本没有阈值窗口**（负例最高 0.727 > 正例 5% 分位 0.675）。
> 所以本地版的拒答**只能靠 Prompt 层**（第 4 条铁律），别再花时间调 Score 阈值。

### 7.4 Rerank 本地没有，要单独决策

云端开了 Rerank（`qwen3-rerank`），本地默认没有。三条路：

| 选项 | 代价 | 建议 |
|---|---|---|
| 不要 rerank | 无 | 先用它跑 baseline（`profile local` 就是这么定义的） |
| 自己实现加权打分 | 小 | ⚠️ **注意**：Dify 官方明确「TopK 与 Score 阈值仅在启用 Rerank 后生效」——自建加权不是真正的 rerank，别指望它替代阈值兜底 |
| 调 API rerank | 需联网 | 想要同等质量就用它 |

### 7.5 提示词一字不改

那 7 条铁律是**实测验证过有效的**（v1→v2：条文号 0/5→3/3、拒答 0/2→2/2）。搬过来时**原样复制**，包括第 4 条那句「只回复：本知识库未收录该内容」。

### 7.6 别急着下线云端

本地版跑通并跑完 A/B 之前，**Dify 那个 demo 是你的退路**：能演示、能验收、结果已知。等本地版在 §6.2 三层测试全过之后，再考虑要不要切换主入口。
